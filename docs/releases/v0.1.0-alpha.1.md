# Chronicle v0.1.0-alpha.1

Chronicle's first release is an **evaluation prerelease** of completed M1/M2:
qualified direct-player stone/air logging and read-only investigation. Evaluate it
on disposable servers. Recovery and the M3/M5/M6 stable-release gates remain
unfinished. This is not comprehensive server protection.

## Included

- Direct-player air-to-stone placement and stone-to-air breaking, with stable
  player/world UUIDs, ordered capture identities and versioned before/after state.
- SQLite schema 2, transactional idempotent writes, bounded queues/readers,
  durability/backlog status and visible coverage incidents.
- `/chronicle inspect`, filtered `/chronicle lookup`, requester-owned fixed-boundary
  pagination, `/chronicle status` and presentation-only `/chronicle reload`.
- Historical player-name resolution, permission checks before asynchronous results,
  and qualified inspection that respects existing protection denials.

The [capture qualification](../CAPTURE_QUALIFICATION.md),
[investigation guide](../INVESTIGATION.md) and [storage guide](../STORAGE.md)
define the exact contracts. MIT attribution and the
[dependency notices](../../THIRD_PARTY.md) remain intact and are bundled in the JAR.

## Runtime and artifacts

| Input | Qualified configuration |
| --- | --- |
| Server | Paper, Minecraft 26.3, build 248; data version 5023 |
| Java | Java 25 |
| Operating systems | Windows and Linux; exact test runners recorded in `VALIDATION.md` |
| Storage | Local SQLite, bundled JDBC 3.54.1.0 / engine 3.54.1, WAL and `synchronous=FULL` |
| Build | Checked-in Gradle 9.9.1 Wrapper, locked/checksummed dependencies |

The plugin refuses unqualified server builds. Folia, Spigot, other Minecraft
versions and other forks are unsupported. macOS is not qualified by this release.

Download these assets from the
[GitHub release](https://github.com/D3V-X3N0/Chronicle/releases/tag/v0.1.0-alpha.1):

- `chronicle-0.1.0-alpha.1.jar`: the installable plugin.
- `SHA256SUMS`: SHA-256 checksums for the plugin and validation report.
- `VALIDATION.md`: exact source commit, artifact hash, local checks and CI evidence.

The separate `paper-test-plugin` JAR produced by a source build is a diagnostic
fixture and is not a release asset. GitHub's automatic source archives are source
code, not installable plugins. Checksums verify download integrity; they are not
signatures or a claim of reproducibility across operating systems.

## Installation and first investigation

1. Start with a disposable Paper 26.3 build 248 server using Java 25 and your
   accepted Minecraft EULA. Stop it before installing Chronicle.
2. Compare the downloaded JAR's SHA-256 with `SHA256SUMS`. PowerShell:
   `Get-FileHash .\chronicle-0.1.0-alpha.1.jar -Algorithm SHA256`.
   On Linux, with all three assets in the same directory, run
   `sha256sum --check SHA256SUMS`.
3. Put only `chronicle-0.1.0-alpha.1.jar` in `plugins/`, then start the server.
   Run `chronicle status` from the console and wait for storage to report `READY`.
4. Grant a test player the permissions they need through your permission manager:
   `chronicle.status`, `chronicle.lookup`, `chronicle.inspect` and/or
   `chronicle.reload`. All default to false, including for operators. Local console
   is trusted; there is no built-in permission-grant command.
5. Outside inspection mode, place stone into air and break it. After the committed
   count advances, run `chronicle lookup time:1h action:block-place,block-break`
   from console. In game, toggle `/chronicle inspect` and click that position to
   investigate it; toggle again to resume ordinary interaction.
6. Stop cleanly, restart, wait for `READY` and repeat the lookup with the same time
   scope. Read any coverage or prior-session warning before interpreting results.

Configuration is created at `plugins/Chronicle/config.yml`; history is stored at
`plugins/Chronicle/history.db`. Reload supports only runtime-detail display and
lookup page size. Storage changes require a restart. Invalid configuration is
preserved and rejected rather than replaced.

## Existing development databases

Before moving from an M1/M2 development JAR, stop the server and make a separate
backup of the whole Chronicle data directory, including any database/WAL/SHM files,
and the world. Verify the database copy in a disposable environment. Do not copy
only a live `.db`, remove its WAL, or replace a failed database to silence an error.

Schema 1 upgrades forward to schema 2; schema 2 from completed M2 remains readable.
The migration's record preservation and failure atomicity are tested. An M1 binary
cannot reopen schema 2, and there is no database downgrade command. This does not
establish world/database backup atomicity or a production upgrade qualification.

## Evidence and limitations

The attached `VALIDATION.md` records the exact release candidate's full build,
packaging/native/database/crash tests, and both disposable Paper harnesses locally
and on Linux/Windows CI. Packet tests use actual loopback players and independently
check durable SQL history after restart. Controlled protection and permission
fixtures qualify only their documented interactions.

The [M2 measurements](../M2_MEASUREMENTS.md) are synthetic index and concurrent
write/query evidence through one million starting rows at the revisions named in
that report. They are not real-server throughput, tick-latency or production-capacity
promises, and were not repeated for version/notice-only packaging.

No rollback, restore, container/inventory logging, hopper, explosion, environmental
or entity logging is included. No retention or backup command exists. Inspection
does not read container contents, and history at a chest location is not chest
logging. Unsupported or ambiguous transitions are not fabricated into complete
records. An accepted queue entry is not durable until committed; crashes can lose
pending records, and a database commit is separate from world-save durability.
There is no hardware power-loss qualification, comprehensive third-party plugin
matrix or claim of production adoption. Keep independent backups.

Report reproducible problems through the
[issue tracker](https://github.com/D3V-X3N0/Chronicle/issues), including this version,
exact runtime and sanitized status/log output. Do not attach private player history,
secrets or production databases.
